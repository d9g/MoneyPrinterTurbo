### P0-2: `_file_hash` 缓存层对大文件全量读入内存，可导致 OOM

**文件**: `app/services/audio/analyzer.py` L30-35  
**代码**:
```python
def _file_hash(path: str) -> str:
    h = hashlib.md5()
    with open(path, "rb") as f:
        while chunk := f.read(8192):
            h.update(chunk)
    return h.hexdigest()
```

**问题**: 对每个音频文件（可能 50-100MB）计算 MD5 作为缓存 key。在 Web 场景下，多个用户同时上传时，每个请求都全量读文件。更严重的是：`analyze_audio()` 先 `_file_hash()` 再 `preprocess_audio()`，等于文件被**读了两次**（一次算 hash，一次 librosa 加载）。

而且 `_analysis_cache` 是进程内 dict，不跨进程/不持久化。多 worker 部署时缓存完全失效。

**修复建议**: 
1. 用文件大小 + mtime + 文件名作为缓存 key（无需读文件内容）
2. 或用文件前 1MB 做 hash（牺牲精度换性能）
3. 缓存应支持持久化（如 SQLite），否则进程重启即失效

## P1 — 高优先级问题

### P1-1: `detect_chorus_segments` 中 `expand_until_valley` 可能越界访问

**文件**: `app/services/audio/features/sections.py` L118-130  
**代码**:
```python
def expand_until_valley(start_f: int, direction: int) -> int:
    f = start_f
    step_count = 0
    max_step = max_chorus_frames // 2
    while 0 <= f < n_frames - 1 and step_count < max_step:
        next_f = f + direction
        if not (0 <= next_f < n_frames):
            break
        if composite_smooth[f] < threshold:  # ← f 可能 == n_frames-1
            return f
        f = next_f
        step_count += 1
    return f
```

**问题**: `composite_smooth[f]` 中 `f` 在循环条件 `f < n_frames - 1` 下可达 `n_frames - 2`，但在 `f = next_f` 之后 `step_count` 递增进入下一轮循环时，条件检查 `0 <= f < n_frames - 1` 可能让 `f == n_frames - 2` 通过，然后 `next_f = f + direction` 可能 == `n_frames - 1`，此时 `composite_smooth[f]` 访问 `n_frames - 2` 是安全的。但如果 `composite_smooth` 长度与 `n_frames` 不一致（虽然代码中对齐过），仍可能越界。

实际风险有限（因前置对齐），但 `expand_until_valley` 的 `f` 在最终 `return f` 时可能等于 `start_f`（没移动），导致 `end_f - start_f == 0`，后续 `seg_composite = composite[start_f:end_f]` 为空数组。

**修复建议**: 在 `seg_composite = composite[start_f:end_f]` 后、`if len(seg_composite) == 0: continue` 之前，增加对 `start_f >= end_f` 的处理。

### P1-2: `acquire_lock` 实现有并发安全问题 — 使用 `threading.local()` 做锁字典

**文件**: `app/services/mv/intent_repository.py` L154-163  
**代码**:
```python
_intent_locks = threading.local()  # 进程内 per-thread 的锁字典

def acquire_lock(self, signature: str) -> threading.Lock:
    if not hasattr(_intent_locks, "locks"):
        _intent_locks.locks = {}
    if signature not in _intent_locks.locks:
        _intent_locks.locks[signature] = threading.Lock()
    return _intent_locks.locks[signature]
```

**问题**: `threading.local()` 是**每线程**独立的。线程 A 创建的锁字典和线程 B 的完全隔离。所以线程 A 拿到的 `Lock()` 和线程 B 拿到的不是同一个锁 → 锁完全无效，无法防止跨线程并发。

此外，即使改成全局 dict，`if signature not in _intent_locks.locks` → `_intent_locks.locks[signature] = Lock()` 这个 check-then-set 也有 TOCTOU race condition。

**修复建议**: 用模块级全局 `dict` + 全局 `Lock` 保护字典创建：

```python
_global_locks: dict[str, threading.Lock] = {}
_global_locks_guard = threading.Lock()

def acquire_lock(self, signature: str) -> threading.Lock:
    with _global_locks_guard:
        if signature not in _global_locks:
            _global_locks[signature] = threading.Lock()
        return _global_locks[signature]
```

### P1-6: `IntentDB.fetch_one` / `fetch_all` 不在事务中，长查询可能读到脏数据

**文件**: `app/services/mv/db/connection.py` L71-78  
**代码**:
```python
def fetch_one(self, sql: str, params: tuple = ()) -> Optional[sqlite3.Row]:
    conn = self._get_conn()
    cursor = conn.execute(sql, params)
    return cursor.fetchone()
```

**问题**: `fetch_one` 和 `fetch_all` 直接在连接上执行，不在事务上下文中。虽然 SQLite 默认 autocommit（每条 SQL 独立事务），但 `check_same_thread=False` + WAL 模式下，如果写事务在 `transaction()` 中执行 `UPDATE ... SET is_latest=0` 然后 `INSERT`，读操作可能读到中间状态（is_latest 全为 0 的瞬间）。

影响有限（因为 `insert_history` 的 UPDATE + INSERT 在同一个 `transaction()` 上下文中，是原子的），但如果 `cleanup_old_versions` 和 `get_latest` 并发执行，可能有问题。

**修复建议**: 对一致性要求高的读查询，用 `with self.transaction() as conn:` 包裹。

**文件**: `app/services/lyrics_parser.py` L103-115

```python
def _xor_decrypt(data: bytes, key: bytes = b"") -> bytes:
    if not key:
        for k in [b"@uttar-3f", b"taobao1234", b"", b"QRC\x00"]:
```

### P2-7: WebUI 中 `_should_run_llm` 的时间比较逻辑可能异常

**文件**: `webui/Main.py`（新增代码中 `_should_run_llm` 函数）

1. **`ChorusSegment` 的 `index` 语义不一致**: `detect_chorus_segments` 返回的 `index` 从 0 开始（L171: `index=i`），但 WebUI 显示时做了 `idx = cs.get("index", 0) + 1`（+1 给用户看）。`chorus_options.append(idx - 1)` 又减回 1。但传给 `_apply_chorus_keywords_callback` 的 `idx` 参数是 0-based 的 `selected_idx`，而 `displayed_segments[selected_idx]` 也是 0-based 索引。逻辑正确但容易混淆。

2. **`mv_plan` 中 `video_prompts[].section_index`**: LLM 输出的 `section_index` 从 0 开始（prompt 中写了 `{"section_index": 0, ...}`），但 WebUI 高潮段匹配时用 `vp.get("section_index") == selected_idx`，`selected_idx` 是 `chorus_options` 中的值（0-based）。如果 LLM 返回的 `section_index` 与 `detect_chorus_segments` 的 `index` 不对应（它们是独立编号的），匹配会失败。代码中也有 `if not matching_prompts: st.caption("该高潮段未匹配到意境方案")` 的兜底，说明开发者意识到了这个问题。

3. **`song_signature` 格式不一致**: `compute_song_signature` 返回 `"meta:artist::title::duration"` 或 `"fp:hash::duration::bpm::key"`，但 `intent_repository.py` 的 `get_latest_by_signature` 直接用 `song_signature` 做 SQL WHERE 条件。如果签名中含特殊字符（如歌名含 `'`），SQLite 参数化查询能防注入，但签名格式中 `::` 分隔符可能与歌名冲突。

## 性能审计

### ⚠️ 潜在性能问题

1. **音频文件双读**（P0-3 已详述）: `analyze_audio` + `preprocess_audio` 被调用两次
2. **缓存层全量读文件**（P0-2 已详述）: `_file_hash` 对大文件全量 MD5
3. **`detect_chorus_segments` 中 `scipy.signal.find_peaks`**: 对长歌曲（5分钟+），`composite_smooth` 数组可能有 ~13000 个元素（22050/512 * 300 ≈ 12920），`find_peaks` 复杂度 O(n)，性能可接受
4. **`compute_audio_fingerprint` 中 `chroma_stft`**: 对 5 分钟歌曲计算 chroma 特征，librosa 内部 FFT，耗时 1-3 秒。但它在 `analyze_audio` 之后再次调用（因为 `mv.py` 单独调 `preprocess_audio` 后传给 `compute_song_signature`），重复计算
5. **WebUI `_init_mv_runtime()` 每次分析都调**: `init_mv_db` 有 `CREATE TABLE IF NOT EXISTS`，重复执行是幂等的，但多了一次 SQLite 连接开销
6. **`material.py` 关键词展开**: 每个关键词展开 2-3 个变体，API 调用翻倍（P2-4 已详述）
